Architecture

Three parties, two trust levels. The suspect writes; the auditor only reads. The change journal is written by triggers, not application code, so the suspect cannot skip it or forge it.

The trust model

  • The suspect is untrusted. Transcript, claims, provenance - all testimony, all checkable.
  • The system of record is ground truth. Its journal is written by triggers, not app code.
  • The auditor holds a read-only handle. It is typed against *Reader protocols and cannot write to the systems it audits.

The audit pipeline

Claims are extracted from the transcript, replayed against the journaled window (before and after every write), and scored deterministically. Writes the agent never mentioned surface as findings, so quiet side effects cannot slip through.

Systems of record

  • SQLite - the reference backend: one database, journal written by triggers.
  • Google Calendar - the first real adapter: incremental sync tokens, a snapshot cache for before-images, actor attribution via event properties.
  • Anything that can answer "what changed between t0 and t1, and who changed it?" can sit behind the same reader protocols.

The human review queue

The queue starts with one open item per standalone finding and per MISMATCH, NOT_FOUND, or UNVERIFIABLE verdict in a sealed audit. An auditor can see what still needs follow-up and trace each change in review state back to the original result through hash-chained receipts that record the actor label, reason, and time. src/subpoena/api/review.py defines the items and transitions, and src/subpoena/api/review_store.py stores the receipts in SQLite and replays them to derive the current state.

Coverage gaps

The audit report lists systems that could not be read or whose change history was incomplete for the call window, with the reason and any affected claim IDs. Those claims are UNVERIFIABLE. The list shows an auditor where the evidence was insufficient for a verdict about what happened. src/subpoena/auditor/engine.py collects the gaps and applies the verdict rules, and src/subpoena/auditor/render.py gives the gaps their own section in the Markdown report.

The revision journal

When a repeat audit of the same call changes a claim's verdict status, the journal appends a hash-chained receipt with the claim ID, old and new statuses, a reference to the later audit, and the time. An auditor can trace the change back to the original sealed result and see which audit reached a different verdict. src/subpoena/api/revisions.py defines and verifies the receipts, and src/subpoena/api/store.py records them when it saves the new audit.
